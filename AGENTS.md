# AGENTS.md — ggsipu_notice

Rules for agents working in this repository. Everything below was read out of this repo
(pubspec.yaml, analysis_options.yaml, .gitignore, lib/, server/, server-new/, test/), not
assumed from another project. Where this repo has no convention, that is said plainly
rather than invented.

## What this is

A Flutter app (`name: ip_notices`, version `1.3.1+20`) that lists notices scraped from
GGSIPU's website (http://www.ipu.ac.in/notices.php), plus the Python backend that does the
scraping. Notices live in Cloud Firestore, are mirrored into Algolia for search, and new
ones are pushed to devices via FCM and OneSignal.

Three deployable pieces live in one repo:

| Piece | Path | Runtime | How it ships |
|---|---|---|---|
| Mobile app | `lib/`, `android/`, `ios/` | Flutter 3.44.3 / Dart 3.12.2 (`sdk: ">=3.4.0 <4.0.0"`) | Play Store / App Store build |
| Cloud Functions backend (current) | `server-new/functions/` | Python 3.11 (`server-new/firebase.json`: `"runtime": "python311"`) | `firebase deploy` |
| Heroku scraper (legacy) | `server/` | Python + Flask + APScheduler (`server/Procfile`, `server/requirements.txt`) | not currently deployed; superseded by `server-new/` |

`web/` and `windows/` exist because `flutter create` made them. Nothing ships from them.

## Local config you must supply (gitignored, and genuinely absent from a fresh clone)

`.gitignore` excludes the files that carry credentials. Without them the app does not
analyze, test or build:

| File | Needed for | Symptom when missing |
|---|---|---|
| `lib/keys.dart` | `oneSignalAppID`, `algoliaApplicationId`, `algoliaApiKey` | `flutter analyze` and `flutter test` fail with `uri_does_not_exist` at `lib/main.dart:8` and `lib/services/algolia_service.dart:2` |
| `lib/firebase_options.dart` | FlutterFire config | generated by `flutterfire configure` |
| `android/app/google-services.json` | Android Firebase | `flutter build apk` fails |
| `key.jks` | release signing (`android/app/build.gradle` `signingConfigs.release`) | release build fails |

`tool/harness/verify`'s `local_config` check reports exactly which of these are missing,
on every tier, so the resulting analyze/test failures are never mysterious.

**Never commit any of them, and never relax the `.gitignore` rules that exclude them.**
The `secrets` check enforces this mechanically on every tier.

## Architecture as it actually is

```
lib/
  main.dart            app bootstrap: Firebase.initializeApp, FCM background handler,
                       OneSignal.initialize, FlutterDownloader, FCM token -> Firestore
  models/              Notice + notice.g.dart (json_serializable, TimestampConverter)
  notifiers/           ChangeNotifier state (FirestoreNotifier, AlgoliaNotifier)
  pages/               HomePage
  services/            FirestoreService, AlgoliaService, ThemeService, logger, locator
  widgets/             presentation only
```

Observed conventions, stated as observation — this repo has no written architecture doc:

- **Service locator, not injection.** `lib/services/locator.dart` registers everything on
  `GetIt`. Services are `registerLazySingleton`, notifiers are `registerFactory`. Reach a
  service with `locator<FirestoreService>()`.
- **`provider` on top of GetIt.** `main.dart` also puts `FirestoreNotifier` and
  `AlgoliaNotifier` in a `MultiProvider`. Both mechanisms are live; follow whichever the
  file you are editing already uses rather than converting one to the other.
- **`lib/models/notice.g.dart` is generated** by `json_serializable` and is **tracked in
  git**. Edit `notice.dart`, then run `build_runner`; never hand-edit the `.g.dart`. The
  `codegen` verifier check fails if the committed `.g.dart` does not match its source.
- **Cupertino-first UI.** `MyApp` builds a `CupertinoApp` and selects a
  `ThemeService.themeData` / `darkThemeData` from `MediaQuery.platformBrightness`. There is
  no theme-mode setting to honour beyond that.
- **Two top-level entry points are `@pragma('vm:entry-point')`** in `main.dart` (the
  Firebase Messaging background handler and the FlutterDownloader callback). They must stay
  top-level and keep that pragma or they are torn out by tree-shaking in release builds.

`lib/` is about 1,760 lines across 18 Dart files. It is small enough to read; prefer
reading it over guessing.

## Risk surfaces

These drove the tier and review policy in `.claude/docs/routing.yaml`. They are the places
where a mistake leaves this checkout:

1. **`server-new/functions/main.py`** — a scheduled Cloud Function that scrapes, writes
   Firestore, mirrors to Algolia and sends FCM messages. **A push notification cannot be
   un-sent.** A dedupe or diff bug here notifies every installed device, repeatedly.
2. **`lib/main.dart`** — Firebase/OneSignal/FCM setup and the write of every device's FCM
   token into the `fcm_tokens` collection. Break this and notifications break for all users.
3. **`.gitignore`** — the only thing keeping `lib/keys.dart`, `android/app/google-services.json`
   and `key.jks` out of git history, where a leak is effectively permanent.
4. **`android/app/build.gradle`** — `signingConfigs.release` for the published app.
5. **`pubspec.yaml` / `pubspec.lock`** — a new dependency ships inside a published mobile app.
6. **`lib/models/notice.dart`** — the shape parsed from live production Firestore documents;
   a required-field change breaks the app against data already in the database.

`server-new/functions/main.py` currently hardcodes `ALGOLIA_APP_ID` and `ALGOLIA_API_KEY`
as literals. That is pre-existing, and the harness does not change it; be aware that the
file is credential-bearing when you touch it.

## Deploying

Cloud Functions deploy from `server-new/` with the `firebase` CLI. Deploys, releases and

## The honest gap

`test/` contains exactly one file, `test/widget_test.dart`, and it is the **unmodified
`flutter create` counter template**: it pumps `MyApp` and looks for a `+` icon and the
text `0`. This app is a `CupertinoApp` showing a notice list. The test cannot pass, and
would not test anything if it did.

So: **this repository has no behavioural test coverage.** `flutter test` is wired into the
`normal` and `full` verifier tiers as a real, required check because a real test file and a
real runner exist — but a green day here will only arrive when that file is replaced with
tests of this app. Until then, `analyze` + `format` + `codegen` + `secrets` is the whole of
what verification proves, and `docs/agents/verification.md` says so in the artifact itself.

## Harness rules

- `tool/harness/verify <fast|normal|full>` decides pass/fail. A check that could not run is
  `incomplete`, never a pass.
- `tool/harness/task` drives task state; `task ready` then `task complete`. `complete` is
  gated and has no `--force`.
- `.claude/docs/routing.yaml` and `tool/harness/lib/classify.mjs` state the same policy in
  prose and in code. **Change both together** — both are hashed into every artifact's
  verification policy fingerprint, so drift invalidates every existing `verify.json`.
- Never hand-write `verify.json`, `review.json` or `adjudication.json`.
